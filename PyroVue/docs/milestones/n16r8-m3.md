# N16R8 M3 — archive API and protocol-3 cutover

## Delivered

M3 implements the real archive/annotation HTTP API, typed owner-loop commands and protocol 3 on all three firmware targets and the embedded browser. The physical N16R8 API smoke passed. Current wire contract: [protocol-v3.md](../protocol-v3.md); approved execution specification: [n16r8-migration-plan.md](../n16r8-migration-plan.md), revision 4421 (unchanged).

The Runs browser is M4, device-note editor/outbox is M5 and ZIP export is M6. The existing editor remains browser-local; the new device annotation API does not migrate local notes. Feather remains the default until M7.

## Implementation

- `ArchiveRoutes.{h,cpp}` / `ArchiveResponse.{h,cpp}`: all command/archive routes, identity header, bounded multichunk bodies, typed owned jobs, weak request continuation and generation-stamped response leases. Four 32-KiB PSRAM slots/eight jobs on N16R8; one 1-KiB command slot/job on monitors. Completed responses copy RAM only; accepted mutations survive client disconnect and cancelled reads are dropped.
- `RunArchiveStore`: bounded metadata preparation (64 raw records or eight events per step), 16-entry PSRAM metadata cache and revision-offset index into the single journal cache. Sample/event pages do not repeatedly rescan earlier file contents. Recovery preserves invalid event suffixes and syncs the validated prefix before replay/append.
- `RunLogService`: normalized Unicode note domain, bounded reducer warmup, durable CRUD/replay, observation-time boundaries and PSRAM mutation scratch. Tombstone retries preserve their original result; original creates still replay after later deletion.
- `NetworkManager` / `HistoryStore`: RAM-only published discovery/current-reading cache; callback-time run/filesystem access removed. History replay copies at most 12 raw or eight coarse points per loop using stable cursors, releases the guard before serialization, and leaves live delivery unsuppressed. The obsolete replay gate is removed; the old queue retains Feather CSV work only.
- `main.cpp`, `config.h`: typed command lifecycle, real monitor behavior, per-chip/per-boot identity on ESP32/ESP8266, protocol 3 / firmware `run-logging-1`. Existing M2 recordings retain originating protocol 2 without an older-wire parser.
- Browser protocol/transport/state: required identity/capability/storage/logging profiles, HTTP-only commands, immutable captured device header/boot/run context, validated final results/errors and no automatic ambiguous retry. Shared operation-ID generation is reused by markers. Existing fixtures were migrated, not replaced with a new framework.

## Actual device proof

Board: ESP32-S3 revision v0.2, MAC/device `aca704126810`, native USB COM6. The workstation cannot reach `192.168.4.1` directly. A temporary client task on the ESP32 used actual HTTP/WebSocket connections to its own AP address; the normal server callbacks, continuation, worker queue and Arduino loop executed every request. A separate temporary owner-loop comparison read the stored CRC-decoded records. Both temporary sources/hooks were removed after proof; no debug endpoint was shipped.

| HTTP samples vs file | All 31 rows matched stored CRC-decoded sequence/time/temperature/fault/flags values; run 1 was never mutated |

| Replay/conflicts | Tombstone retry returned the original revision 4; create retry after deletion returned original revision 2; changed operation/revision returned 409 |

The final successful smoke emitted `M3_SMOKE_PASS`. Bench runs 2–4 were consumed and explicitly deleted, leaving the latest allocated ID at 4 and the owner's saved run 1 intact. The next new run is therefore 5, not 2. No filesystem image, format, run-ID rollback or automatic deletion was used.

Runtime fixes found by this smoke: the nested 4-KiB metadata stack buffer overflowed loopTask during Start (decoded backtrace); parsing now reuses store PSRAM scratch, and preparation reuses the idle journal buffer rather than another 2-KiB stack array. Immediate error JSON needed an explicit NUL and a response-present guard so a later handler could not replace a known 413 with 400. Tombstone normalization needed in-place default initialization rather than zeroing its nonzero Untimed enum. These paths passed after correction; the loop stack was not enlarged to hide the problem.

## Normal firmware deployment

After removing the temporary client and owner-loop hooks, the final pipeline passed: 127 Node cases, typecheck, lint, bundle build/current check, all three firmware builds and firmware-only N16R8 upload on COM6. The final bundle is 260,622 bytes / 78,829 gzip bytes. Normal N16R8 static RAM is 53,716 bytes and flash 988,449 bytes; those are build figures, not a heap-soak claim.

Actual serial `i` after the normal image reboot reported 16,777,216 flash bytes, 8,388,608 PSRAM bytes, LittleFS mounted with 10,354,688 total / 28,672 used bytes, `run=4 active=0`, no logging error and `start=ready`. The temporary client, hooks, host smoke sources/binary and browser server were removed/stopped. No further upload is required from the owner; reload the web app for protocol 3.

Proceed to M4's `ArchiveClient`/`RecordedRunStore` and saved-run selection/graph integration. Use the real M3 endpoints and existing strict archive validators; keep actual device controls independent of the viewed run. Do not build another temporary readback harness.
